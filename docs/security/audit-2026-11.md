# Security audit — phase 10 (2026-11-13)

Internal audit of the HMS before its first installation in a hotel. It was
done by the development team (no external penetration test yet, see
"Residual risks"). Every fix below is covered by an automated test or by the
restore drill, and the tests run in CI.

## Scope and threat model

| Who | Can | Main risks |
|-----|-----|-----------|
| A device on the hotel network (staff PC, guest on a badly separated Wi-Fi) | Reach the server's HTTPS port | Password guessing, spoofing, exploiting a bug without an account |
| A staff member with a low-privilege account | Use the API directly, not only the screens | Reading or changing what their role does not allow; another hotel's data |
| Someone with a stolen session (unlocked tablet) | Act as that user | Escalation (new password, disabling 2FA), destroying data |
| An application bug | Run a query without the right filter | Leaking another organisation's or hotel's data |
| Someone who obtains a backup file | Read it | Guest personal data |

Out of scope: the host operating system and Docker, physical security of the
server, the hotel's Wi-Fi configuration, SiteMinder's side.

## Method

* **Automated, in CI** (`.github/workflows/ci.yml`):
  * every API operation listed in the OpenAPI schema (226) is called without
    a session (must be refused), with a cookie session but without the CSRF
    header (must be refused), with another organisation's hotel (must not
    exist) and by a user whose role has no permission (must be refused):
    `backend/tests/test_security.py`. A new endpoint is covered automatically;
  * database invariants: every table has row-level security or is explicitly
    exempt, the API's role has no TRUNCATE/REFERENCES/TRIGGER and no
    UPDATE/DELETE on append-only tables, the cross-tenant functions are the
    expected five, each with a fixed `search_path` and not executable by
    PUBLIC: `backend/tests/test_tenancy.py`;
  * the whole backend test suite runs as the least-privilege role, so row-level
    security is exercised by every test;
  * Bandit rules (`ruff` rule set `S`) on the backend code; `pip-audit` and
    `npm audit` on shipped dependencies.
* **Restore drill on the production stack** (`deploy/tests/restore-drill.sh`):
  production mode, database roles, backup and restore through the API,
  forwarded-header spoofing.
* **Manual review**: authentication and sessions, CSRF, authorisation,
  tenant isolation, SQL construction (every `text()` with interpolation),
  secrets and encryption, PDF rendering, channel manager input, transport and
  headers (Caddyfile), logging, backups, the desktop shell's capabilities,
  and the accuracy of `docs/architecture/04-security.md`.

## Findings

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 1 | **High** | **Client IP address could be chosen by any device on the hotel network.** Caddy trusted `X-Forwarded-For` from private address ranges (`trusted_proxies static private_ranges`), and uvicorn takes the left-most address of that header. In a LAN installation every client is in a private range, so a device could send its own header and appear as any address: unlimited password guessing (the per-IP login limit is defeated by rotating addresses) and forged addresses in the login history and audit trail. | **Fixed.** Caddy is the edge and trusts no client header (`HMS_TRUSTED_PROXIES` only when another proxy is in front). Verified by the restore drill: a login sent with `X-Forwarded-For: 203.0.113.77` is recorded with the real address. |
| 2 | **Medium** | **The API connected to PostgreSQL as the database superuser.** Any bug reachable by a user, or an injection, would have had full power: schema changes, disabling the append-only triggers, reading every tenant. | **Fixed (migration 0010).** The API logs in as `hms_api` (member of `hms_app`): rows only, no DDL, no TRUNCATE, no UPDATE/DELETE on the audit log and login history, no DELETE on financial records. Migrations run in a separate `migrate` service as the owner; the API container never has the owner's password. In production the API refuses to start with a role that is superuser, bypasses row-level security or owns the tables. |
| 3 | **Medium** | **Tenant isolation relied on application filters only.** All queries filter by hotel today (verified by tests), but one forgotten filter in a future change would leak another organisation's or hotel's data. | **Fixed (migration 0010).** Row-level security on every tenant table: organisation boundary always, hotel boundary for hotel requests. Without a declared tenant nothing is visible. Tests: a second organisation is invisible through the API and in raw SQL, and writes into it are refused. |
| 4 | Medium | **No way to recover an account whose 2FA phone is lost**, short of editing the database by hand (which invites unsafe workarounds such as sharing accounts). | **Fixed.** *Reset two-factor authentication* for administrators (`users.manage`, not on one's own account, not on a super administrator unless one is): switches 2FA off, ends all the user's sessions, audited. |
| 5 | Low | **Password re-checks of a signed-in user were not throttled** (change password, disable 2FA): a stolen session allowed unlimited guesses of the account password. | **Fixed.** 5 attempts per 5 minutes per account, shared by all API processes; the same check protects the restore confirmation. |
| 6 | Low | **Login attempts against unknown e-mail addresses were shown to the super administrators of every organisation** (only relevant when one server hosts several organisations). | **Fixed.** Shown only when the installation has a single organisation (enforced by a row-level security policy). |
| 7 | Low | **The installation guide suggested base64 database passwords**, which may contain `/` or `+` and break the connection URL (the stack fails to start). | **Fixed.** Hexadecimal passwords (`openssl rand -hex 32`). |
| 8 | Info | **The security document described protections that do not exist**: a general per-IP rate limit in Caddy, an automatic dependency update bot, a lint rule banning `dangerouslySetInnerHTML`, upload checks and personal-data retention (no upload or retention feature exists yet), "double-submit cookie" CSRF (the real mechanism is a per-session token), recovery codes and mandatory 2FA per role. | **Corrected** in `04-security.md`; missing features are marked "not built yet". |
| 9 | Info | **Development dependency `vitest` 3.2.7** pulled `tinypool` and `@vitest/mocker` versions with published advisories (prototype pollution leading to code execution in the test runner, path traversal in browser mode). Not shipped to hotels and not exploitable as used (local unit tests in jsdom), but a developer machine is worth protecting. | **Fixed.** `vitest` 4.1.12; `npm audit` (all dependencies) reports nothing. |

Checked and found sound (no change needed): Argon2id hashing with transparent
rehash; opaque 256-bit session tokens stored hashed; idle and absolute session
expiry; `httpOnly; Secure; SameSite=Strict` cookie; identical answers for
unknown e-mail and wrong password; account lockout; per-permission filtering
of WebSocket events and origin check; parameterised SQL (no SQL text is built by
string interpolation in the application code, which Bandit rule S608 checks in
CI; migrations build DDL from constants of their own file only); card-number guard on
free-text fields; Fernet encryption of recoverable secrets with the key outside
the database; channel XML parsed with `defusedxml`, message bodies redacted;
PDF rendering without network access; append-only financial records; the
desktop shell grants no command to pages loaded from the server; Caddy security
headers (HSTS, CSP without inline script, `X-Frame-Options: DENY`).

## Residual risks and recommendations

* **No external penetration test yet.** Recommended before hosting several
  organisations on one server or exposing a server to the Internet.
* **No general request rate limit** (only sign-in and password re-checks).
  A device on the network can load the server with legitimate-looking
  requests; acceptable on a hotel LAN, worth an upstream limit for a public
  deployment.
* **Row-level security protects against application bugs, not against
  arbitrary SQL** run as the API's role (which could set the tenant variables
  itself). Parameterised queries remain the defence against injection.
* **2FA: no recovery codes, cannot be made mandatory per role.**
* **Backups are not encrypted** by the backup service: they are readable by
  root only on the server, and copies taken off the server (recommended) must
  be stored encrypted or physically protected. Encrypted fields inside stay
  encrypted without `HMS_DATA_KEY`.
* **Unsigned installers** (Windows SmartScreen warns) and no automatic update
  of the desktop shell (phase 9).
* **No automatic dependency updates.** `pip-audit` and `npm audit` fail the CI
  on known vulnerabilities in shipped dependencies; Rust crates of the desktop
  shell are not audited automatically (`cargo audit` is not installed in CI).
